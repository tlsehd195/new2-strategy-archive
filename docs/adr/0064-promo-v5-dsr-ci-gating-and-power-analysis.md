# ADR 0064 — promo-v5 기본값: DSR·부트스트랩 CI를 판정 게이트로, 계산 불가는 INSUFFICIENT_DATA; 재현 가능한 검정력 분석

- 상태: Accepted (코드·테스트·합성 검정력 측정; 기준은 강화만, 완화 없음)
- 날짜: 2026-11-10
- 요청: 동동, 2026-11-10 전수 감사 지시문 §6 (통계 검증), §7 (검정력), §12 (상태 무결성)
- 감사 문제 ID: T-01 (Critical), T-02 (High), T-03, T-04, T-05, S-01 (Medium) — `run/audit/AUDIT_FULL_20261110.md`

## 맥락
- **T-01·T-02**: `pipeline.robustness()`는 DSR과 부트스트랩 CI를 `"pass": True, "gating": False`로만 기록했다.
  - 그래서 DSR 0.59인 후보나 CI가 0을 포함하는 후보도 VALIDATION_SURVIVOR가 될 수 있었다.
  - 재현: `tests/test_promo_v5_20261110.py`의 EDGE2가 v3에서는 통과하고, v5에서는 REJECTED다.
- **T-03**: 기본 설정은 `promotion_v3.json`이었다. 그런데 v4(PBO 0.05)도 있었고, 문서마다 가리키는 버전이 달랐다.
- **T-04**: DSR·PBO 시행 집합은 "그 컨텍스트의 모든 DEV 시계열"이었다.
  - 여기에는 검증 통과 후보의 이웃(robustness neighbours)도 들어간다. 그래서 평가 순서에 따라 시행 수와 결과가 달라졌다.
- **T-05**: 현재 게이트의 1종·2종 오류, 검정력, 최소 검출 효과를 재현 가능하게 계산하는 도구가 없었다.
  - 이전 측정(ADR 0022, 0048)은 v3 게이트의 복사본을 썼다.
- **S-01**: `dev_evaluate`는 OK 기록을 먼저 쓰고 DEV 시계열을 나중에 썼다.
  - 그 사이에 프로세스가 죽으면 재개 때 그 전략을 건너뛴다. 그러면 그 전략이 DSR·PBO 시행 집합에서 조용히 빠졌다.

## 결정
1. **`promotion_v5.json` = 단일 기본값.** v4에 robustness 키 여덟 개만 더했다(나머지 절은 v4와 같음, 테스트로 고정).
   - `dsr_gating`: true, `min_dsr`: 0.95, `dsr_min_days`: 30
   - `dsr_trial_set`: `search_pool`
   - `ci_gating`: true, `ci_bootstrap_B`: 2000, `ci_lower_bound_min_bp`: 0.0, `ci_min_days`: 30
   - 버전과 해시는 컨텍스트와 모든 robustness 기록(`config_version`)에 남는다. v1~v4는 기록용으로 그대로 둔다.
2. **판정 규칙.**
   - DSR: 계산할 수 있고 0.95 이상이어야 통과한다. 0.95는 Bailey·López de Prado의 관행값으로, 선택 편향을 보정한 뒤 SR > 0일 확률 95%를 뜻한다.
   - CI: 검증 일별 순수익의 95% 정상(stationary) 부트스트랩 하한이 0 bp보다 커야 통과한다.
   - 실패한 검사가 하나라도 계산된 실패이면 REJECTED다.
   - 실패한 검사가 모두 계산 불가이면 BLOCKED_STATISTICS(사유 `INSUFFICIENT_DATA: …`)다. 계산 불가는 일수 부족, 시행 2개 미만, 분산 0 같은 경우다.
   - DSR·PBO는 DEV 시행이 늘면 다시 계산해 재개한다. CI 일수 부족은 검증 구간이 늘지 않으므로 재개하지 않는다.
3. **시행 집합 = 탐색 풀.** 각 전략의 최신 DEV 시계열 중 `search_pool()`(등록된 시드·탐색 제안)만 쓴다. 이웃은 빠지므로 평가 순서에 따라 결과가 바뀌지 않는다.
4. **DEV 시계열을 먼저 기록한다(S-01).** 이제 중단되면 "기록 없는 시계열"만 남고, 재개 때 다시 평가된다. 판독기는 최신 행을 쓴다.
5. **검정력 분석** `run/discovery/power_analysis.py` + `config/power_analysis_v1.json`
   - 표준 라이브러리만 쓰고, 합성 자료만 쓰며, 시드를 고정한다.
   - 저장소의 실제 함수(`stats_mc.stepm`, `engine_lib.deflated_sharpe`, 정상 부트스트랩)를 promo-v5의 알파·기준으로 그대로 쓴다. 그래서 게이트가 바뀌면 결과도 바뀐다.
   - 모형: 연 SR을 일별 평균으로 바꾸고, AR(1) φ=0.1, t(4) 잡음을 쓴다. 배치는 10개이고 그중 진짜 우위는 1개다. DEV는 1000일, DEV 시행은 900개다.
   - 계산 항목: 1종 오류(FWER, CI·DSR 무효 통과율), 검정력, 2종 오류, FDR, 80% 검정력 최소 검출 SR, 80% StepM 검정력에 필요한 검증 일수(정규 근사). 각 항목을 4개 시나리오(창, 배치 순번, 국면 절반)별로 구한다.
   - 결과: `run/audit/evidence_power_20261110/power_v1.json`
     - 설정 sha256 411d0343…, promo-v5 해시 619b16b9a8504100, Python 3.13, 1930초
     - 시뮬레이션은 시나리오·SR당 40회다. 비율의 표준오차는 최대 약 ±0.08이다.

해석:
- **1종 오류는 지켜진다.** SR 0에서 StepM FWER은 0~0.025다(40회 중 최대 1회). CI 무효 통과율은 0~0.05, DSR 무효 통과율은 0이다. 선택 게이트로 쓸 때(무효 900개 중 최고) DSR 통과율도 0이다.
- **검정력은 매우 낮다.** 네 시나리오 모두 SR 4까지 80% 검정력에 닿지 않는다(상태 UNDETERMINED_POWER).
  - BTC/ETH 검증 창의 8번째 배치(α=2.37e-4)는 연 SR 4에서도 전체 통과 18%, SR 2에서 0.5%다.
  - 새 6개월 창은 SR 4에서 28.5%, 새 12개월 창은 SR 3에서 31%, SR 4에서 64%다.
  - 국면 절반(88일)은 SR 4에서도 9%다.
  - 정규 근사로는 연 SR 2를 80%로 잡으려면 검증 일수가 약 1,600일(새 창) ~ 2,700일(k=8)이다. 6개월 창으로는 구조적으로 불가능하다.
- **v5가 막는 것은 거짓 양성이지 진짜 우위가 아니다.** DSR 통과율은 연 SR 2에서 10~20%, SR 4에서 90~95%다.
  - 지금까지 찾은 후보는 DEV 총 SR 1~2 수준이다(ADR 0057). 그래서 v5가 새로 막는 것은 주로 우연 수준의 후보다.
- 결론: 기준을 낮추는 것은 답이 아니다(지시문 금지 1, 5). 증거량을 늘리는 설계가 필요하다. 예를 들면 긴 전향 창, 배치 축소, 바스켓 단일 가설이다(ADR 0022·0023 제안과 같음).

## 영향
- 기본 설정 해시가 바뀌므로 evolve 실험 컨텍스트가 새로 생긴다.
- 이전 컨텍스트의 기록과 판정은 그대로다(소급 적용 없음). 기록된 실제 검증 배치(ADR 0012 R3 등)에서 생존자는 0건이었다.
- 잠금 캠페인 메커니즘 테스트 두 개는 두 번째 생존자가 필요하다. 그래서 v3을 명시해 메커니즘만 시험한다.
